Scalability on the software side, this is, I would say, it's very interesting because in the first year where we built our software, we ran into some customers who had ridiculous queries. You have to think about like the way GraphQL Federation works is you have this monolithic schema. You send a query to the, you have the router, that's the API gateway. And the router, it takes this GraphQL query and then looks into the query. And like I said earlier, GraphQL Federation is like you take a tree and you cut it into subtrees. And each service is responsible for a subtree. If I write a query that covers some part of this tree, it needs to be resolved by always a different combination of subtrees. And this gets especially complicated to figure out what to do is when you have abstract types like unions or interfaces. And let's say one service implements some structs that are members of a union. Another subgraph implements some other structs. We call this query planning, very complex engineering behind that to figure out how do we get the data and how do we get it in the right order, and in the end when this process is done, we have a query plan, which, again, it's a tree of fetches. By the way, if you learn programming and you think data structures are stupid, we do a lot of things with data structures and trees and everything, and you do tree walking every day, and I personally love tree walking from a mental model like walking through ASTs. I love it and transforming ASTs. It's fun. But okay, coming back to this scalability issue, we had customers who would send more than 10 kilobytes of query to the router. And then the router for I don't know, a minute or something tries to build up query. And so we had issues where we needed to figure out, okay, how can we built caches so that the query planner can look up things faster so that query planning time is faster. Now, like our p95 query planning time is like 10 seconds, which is still not good enough. We also build a query planning cache, because when you start a new router or when you send a router a new config, that cache is empty. We also build a heuristics based system that looks into your analytics and builds a list of queries we should warm up a router before it gets a new config. That means you never really plan a query, because we have planned it ahead of time. That's quite smart. And it helps us to make the router extremely efficient. One other problem we had is with this customer with those weird queries. As a solution, we build to that reduces the query size by 99%. It's actually pretty, pretty cool. So I built an algorithm that would traverse this query. And so we would build a hash map where we keep track of all the selection set in this gigantic query, and then try to figure out do we have duplicate And then if you find these duplicates, you go from the leaf nodes all the way up step by step to the parent nodes and you replace all duplicate selection sets with a single fragment. A fragment is like a reference to a selection set, which you can then with an inline fragment, you can inline it back.
